# 技术范式雷达设计说明

## 1. 要捕捉的对象

系统的输出对象不是论文、代码仓库、博客或产品，而是一个“可被证据支持、也具备现实承接势能的技术范式假说”。普通论文、KOL/LessWrong 原创思想文章和原生代码实现都只先提出机制假说；正式 Technical Report 则可能同时提出若干相互独立的架构、数据或学习机制，抽取层必须分别保留，后续再按共同 background 聚合。

Technical Report 不再一次性生成多套完整档案与 Rubric。报告正文先经过一次轻量机制索引，只保存名称、路线、最短 intervention 与定位证据，不在索引阶段重复生成完整技术叙事；随后每个机制单独补齐背景、机制、因果链和所选类型 Rubric。机制总数不设上限，但调度成本按真实模型调用计算：一次从原点队列取出只处理 `PARADIGM_TECHNICAL_REPORT_MECHANISM_SLICE` 个未完成机制，索引、已完成结果和逐机制失败次数写回父原点，下轮优先处理未尝试机制。新候选先保存，再提交父报告进度，保证异常最多重算而不会形成“机制已完成、候选不存在”的永久漏项。这样索引 JSON 不会随“机制数 × 完整字段”失控增长，单项结构失败也只影响一个机制。System Card、Model Card 或 Whitepaper 若没有独立技术机制，可以形成“已审阅但无机制”的有效结论，不会被当作系统故障永久重试。

以 World Model 为例，Genie 和 V-JEPA 2 应被描述为谱系里的关键节点：它们分别改变了可利用的数据来源、状态预测方式以及与机器人行动系统对齐的路径。系统要捕捉的是这种能力边界与技术前提的改变，而不是模型名称本身。

发现层不再依赖一组散落在代码里的热门关键词。`taxonomy/frontier_landscape.json` 是版本化的前沿覆盖地图，横向覆盖基础模型、reasoning/软件 Agent、多模态/语音/3D、World/Spatial Model、具身/触觉/自动驾驶、AI4S、数据与学习范式、ML 系统/端侧/硬件、安全对齐和评测治理；纵向再由 Rubric 区分架构、算法、数据、学习、推理、行动闭环、系统与科学发现等 intervention 层。领域术语只是第一条车道，系统还会独立查询重点研究者完整姓名、正式报告/系统卡等文档类型、官方研究索引、LessWrong/Alignment Forum 官方 RSS、手工核验 KOL Feed、已核验官方 GitHub 组织的新仓库、HF 策展与人工补录。OpenAlex 仍定位为已知路线的高精度索引，不承担未知术语发现；未知概念可从具名作者与思想源进入。官方仓库车道按 `created_at` 倒序分页，遇到窗口外条目才停止，不使用每组织固定 Top-K；中途页失败会标成覆盖缺口而不是零命中。仓库若链接稳定外部材料，以外部材料为原点；若结构化 README 与代码接口本身首次定义了可复核 intervention，则形成 `original_implementation` 原点。普通 SDK、demo、聚合列表和信息不足的 README 只留审计。每次运行在审计中逐领域、逐车道、逐学术索引请求、逐 Feed 和逐官方入口区分命中、过滤、零命中、限流、失败和未执行。因此空报告只能说明在覆盖健康的前提下没有候选通过联合门槛。

## 2. 证据层级

### A. 原点证据

- 原始论文、预印本
- 研究机构/作者的技术博客
- 前沿组织的正式 Technical Report 与高信息量官方发布
- OpenReview 公开投稿
- KOL 个人博客、LessWrong / Alignment Forum 中给出可执行机制或可证伪预测的原创思想文章
- 已核验官方组织中以结构化 README 和代码接口首次定义技术 intervention 的原生实现

只有这一层可以生成范式假说。

### B. 扎实度证据

- 清晰机制与可核对实验
- 同行评议与作者回复
- 引用网络中的承接关系
- 独立复现和跨任务验证

### C. 扩散证据

- Hugging Face 收藏/讨论
- GitHub 实现、复现和派生工作
- Hacker News 等技术社区讨论
- 后续论文或技术博客的二次解读

扩散层不能把一个弱技术“投票”成新范式，只能提高或降低已有范式假说的可信度。

发布者证据与扩散证据需要联合解释。前沿组织的正式 Technical Report 具有天然的验证与传播势能，进入优先解读；普通论文不能只凭一个知名机构署名直接入选。发布者背景无法核验时，必须看到跨来源实质讨论、独立复现、产品承接或高关注研究者的技术解读，否则留在观察池。

发布者目录采用“召回与背书分离”的四层结构。官方研究索引决定主动抓哪些页面；`established` 组织只登记具名研究团队或实验室，不登记整所大学；`monitored` 组织保证新模型厂商和机器人公司不漏看，但品牌本身不提供准入捷径；重点研究者必须完整姓名精确命中，并由个人主页或学术 ID 交叉核验，结果也只算 `verified`。网页 `og:site_name`、模型品牌或作者自述不能替代 owner 身份。具体目录见 [前沿机构与研究者 Watchlist](FRONTIER_RESEARCH_WATCHLIST.md)。

外部证据在进入评分与写作前必须做相关性审计。arXiv 与 Hugging Face 对同一论文的同步收录只算一个事件；论文日报、awesome list 和关键词聚合仓库不算实现。KOL 或社区信号不仅要记录互动数字，还要保留讨论的技术亮点、争议或用途。作者本人按工作标题发布的帖子只用于对齐身份、简介与公开主页，不算独立二次验证。

社区覆盖分成两层：Tavily 负责发现被公开搜索引擎索引的 X、Reddit、小红书页面和独立技术博客，不参与准入或声量计分；获批的 Reddit OAuth 与可选 X API 才提供官方搜索及互动指标。每个候选保存本轮平台覆盖状态，报告必须区分“没有配置/索引不完整”和“官方搜索后未检出”。社区用户正文只在当轮综合时存在，完成中文提炼与身份核验后清除。

官方仓库与独立验证必须分账。论文项目页直接关联的仓库可以通过真实 star/fork 说明采用与传播势能，但不能同时在“独立实现”和“独立讨论”两栏重复加分。原生实现仓库可以提出机制假说，但同一个仓库仍不能证明自己被独立验证。只有非作者团队的复现、后续论文、产品采用或有内容的第三方分析才属于独立承接。

思想原点同样分账。KOL 自己的博客、X 转发和 LessWrong 原帖合起来仍只算一次提出；curated/frontpage/karmaThreshold 是选择信号，不是精确热度。只有其他主体围绕机制进行实质讨论、实现、引用或采用，才能形成承接。关键词如 RSI 只用于发现和跨材料对齐，必须在问题定义、作用对象和闭环含义一致时才可聚成路线。

## 3. 版本化 Rubric 决策

技术判断不再要求模型凭整体印象直接输出 0–10 分。最小决策单元是一个带证据的二分或选择题：模型选择 option 并写出材料依据，程序再按 `rubrics/paradigm_rubric.json` 中版本化的 value、weight 与阶段阈值确定性计算。common Rubric 检查问题真实性、机制可复述性、因果链、能力边界、迁移空间和实验控制；architecture、algorithm、learning_paradigm、data、inference、agent_action_loop、embodiment、world_model、scientific_discovery、systems、evaluation 等类型分别加载不同问题。World Model 专项题检查状态动力学和决策接口，AI4S 专项题检查真实科学对象、领域约束、实验验证和发现闭环。发布者、独立复现、二次讨论、研究轨迹与多工作汇聚由程序根据结构化证据自动回答，模型不能自行抬分。

初筛前还有一层普通论文资格预筛，用来落实“召回不等于值得直接消耗完整 Rubric”。它按分析批次一次读取多条 title/abstract，但每条必须原样返回 fingerprint，不能排序或漏掉输入；只对明确的综述、纯 benchmark/数据集、窄领域套用、局部工程优化和无机制公告给出终止结论。任何信息不足、边界不确定、输出漏回或身份异常都进入完整 Rubric 或保留 pending。正式报告、思想原点、原生实现、重点研究者和显式补录绕过这层便宜判断。已通过资格预筛但完整抽取失败的原点会记住资格结果，下轮不重复支付预筛调用。

完整初筛分为“直接深挖、边界复核、观察/拒绝”三种执行语义。普通材料仍须达到初筛 Rubric 的深挖规则；来自正式 Technical Report、重点研究者网络或显式审计补录的高势能原点，如果技术答案完整且落在观察区间，会获得一次深挖复核，避免单次模型边界判断误杀。这个通道只增加研究注意力，不改变最终 Rubric，也不允许弱技术凭名气进入报告。

以下现象会在对应 Rubric 问题取得低值，而不是由一个模糊的“新颖性 5 分”直接硬拒绝：

- 只在单一 benchmark 上小幅提分
- 只减少少量显存、延迟或参数，未改变可实现能力
- 只替换成熟流水线中的一个狭窄组件
- 只换一个垂直数据集，未提出可迁移的数据或学习方法
- 只有营销命名，没有可复述的机制
- 只有高声量，没有实验、评审、复现或合理技术解释
- 发布者身份/轨迹无法核验，同时没有实质二次讨论或承接

效率改进并非一律排除：如果它把原本不可实现的能力变成可实现，例如把推理成本降到能支持持续在线学习，它仍可能改变范式边界。

## 4. 人物追踪边界

系统先识别贡献结构，再决定追踪谁。默认覆盖前三位作者、末位/资深作者和重点名单中的作者；arXiv 官方 HTML 或项目页明确给出共同一作/通讯关系时采用官方标注。大型合作论文不能被写成“名单中最有名者的论文”。研究连续性必须由代表作、年份、机构和主题承接支持。教育、导师、过往任职只在 ORCID、个人主页或本人公开简介明确给出时记录，不能从共同作者关系推测。

联系方式只接受公开专业来源：个人主页、机构主页、ORCID、Semantic Scholar 等学术档案以及作者明确公开的邮箱。不根据姓名和域名猜测邮箱，不收集私人联系方式，不推断创业意愿。人物名先经过语法安全闸门，邮箱、URL、TeX/版式残片、数字或拼接联系方式不能成为人物实体。已经通过研究 Rubric 的路线如果尚未形成至少一份可核验人物背景与联系方式检索记录，会保留为 `pending_deep`，而不是降低技术结论或发送残缺人物章节。

人物增强采用分层核验：高优先级原点在初筛前读取 arXiv HTML 正文与论文项目页；若 HTML 尚未生成或转换失败，则回退读取官方 arXiv PDF。其他通过初筛的候选在深挖阶段补齐作者主页、公开职业邮箱、贡献角色、项目页和代码入口。团队集体署名可以通过精确别名核验发布组织，但不生成个人档案；数百人系统报告没有官方贡献标注时，也不把末位作者机械解释为资深作者。Semantic Scholar 只有显式启用并配置获批 Key 时才提供作者图谱与主页，没有 Key 时绝不匿名请求；OpenAlex 的已知 ID 和姓名搜索结果都必须用当前论文题目交叉核验，旧状态中只有“查过 OpenAlex”或同名命中的记录不具备交付资格；ORCID 补充任职、教育经历、研究者 URL 与公开邮箱；只有已核验的个人主页才会继续检查公开 `mailto:`、LinkedIn 和 GitHub 链接。若配置 X API，还会用工作原始标题搜索发布账号，只有显示名能与论文作者可靠对齐时才补入公开简介。内部研究档案可以保留待补全线索；确定性人物索引只使用具备最低背景、已完成联系入口检索，并有直接身份锚点或当前工作对齐记录的档案。没有公开联系方式时保留检索记录和最低可确认背景。

## 5. 从候选到研究 Memo

Rubric 只负责上游筛选与审计，不进入最终交付。每一份召回材料都会完成初筛 Rubric；达到深挖规则的候选和高势能边界复核候选都会进入综合，不再固定取前 30 篇或前 16 条路线。综合 Agent 必须调用 `technical-mental-model` 方法：先选择一条能统摄技术的训练、推理、表示或行动流程，用二到四句建立低分辨率运行图，再沿二到五个关键理解缺口递进下钻。每一层都区分来源事实、解释性压缩、推断与未知；只有模块清单、没有观察坐标或递进纠偏的结果会触发重试。

研究总编辑会按共同 background 和能力边界把多篇候选重组成少数技术路线，先写约 500 字的本期总览，再从旧瓶颈、设计哲学、技术落地、路线分歧、客观传播、人物连续性和应用价值连贯展开。技术解释先交付低分辨率抓手，再沿同一运行图提高分辨率，不按论文模块平均用力。心智模型字段只作为写作检查面，不能原样输出为固定栏目。完整方法见 [从低分辨率到高分辨率的技术心智模型写作法](MENTAL_MODEL_WRITING_METHOD.md)。

最终报告不使用总分表、分项评分表、证据 dump 或一份材料一个固定卡片。正文证据以 Markdown 链接和客观数字自然嵌入论证；行内粗体只强调关键词与判断。每条路线在技术解释中必须包含一段简短的“讨论势能判断”，沿“当前阶段结论 → 最有辨识度的非作者讨论/复现/采用事实 → 平台覆盖与未知边界”公开判断依据。总编辑只读取经过过滤的 `momentum_evidence`：作者自发帖和 `indexed_discovery_only` 搜索索引不会进入该证据包；官方实现可以说明被看见，但必须与独立承接分账。该段不是内部思维链，也不展示势能分数；没有实质响应时要直接写证据不足。模型写完后，报告器直接从交付安全的人物档案和候选的统一原点类型（`PRIMARY_PAPER`、`TECHNICAL_BLOG`、`CONCEPT_ESSAY`、`ORIGINAL_IMPLEMENTATION`）确定性生成“关键人物与公开联系入口”“原文与一手资料”两个索引，并逐条验证每条路线具备势能判断、人物核验记录和至少一个安全的真实 URL；不让模型负责记忆、改写或猜测这些字段。除此以外，路线草稿和最终全文中的**每一个** HTTP(S) URL 都必须逐字存在于证据、已核验人物档案或确定性索引：一个有效论文链接不能为另一个猜测的公司页面“兜底”，路径大小写也不得擅自改写。URL 先经过永久链接规范化：Hugging Face `resolve` 链接改为稳定 `blob` 页面，带 `Expires`/`Signature` 的 CDN 对象 URL 会被拒绝，抓取器即使跟随跳转也保留原始 canonical URL。所有解释使用中文转述，英文摘要、英文长句、字段直出以及“真正意义上的新范式”等绝对化结论会触发一次终审重写；重写后若仍存在事实性或交付阻断问题则停止任务。Memo 目标字数与粗体数量属于终审提示和审计项，轻微偏离不再销毁整轮研究结果。

## 6. 跨周增量

- 证据指纹：优先 DOI / arXiv ID / OpenAlex ID / 稳定 URL
- 内容签名：标题、摘要、作者、机构、学术标识
- 报告签名：稳定路线键 + 证据集合 + 核心机制 + 客观指标量级。Rubric 变化不会单独触发重复发送

新候选会用路线名、共同 background、机制词、谱系和覆盖领域与历史路线图保守匹配，不再只按本周模型临时生成的 canonical key 做精确等号。观察池与已报告路线每周都会用近期 GitHub、Hacker News、X 与聚合支持信号刷新，但“检测到变化”不等于“具备更新资格”。历史路线只有出现已核验独立复现/采用/实现、达到类型阈值的指标量级变化，或被上游明确审计为独立且直接关联本机制的实质讨论时才可重新进入报告；泛主题讨论、只提论文名、作者自发帖、搜索索引和普通 `+1` 不构成进展。`historical_reactivated` 路线必须在正文原样链接至少一条 `current_uptake_evidence`，只解释本周新增事实，不重复旧证据。

发现采用分层时间窗。普通 arXiv 地景、OpenAlex、OpenReview 与 Hugging Face 只使用 `SOURCING_LOOKBACK_DAYS=7`；正式 Technical Report、重点研究者、官方研究入口与官方仓库发布事件使用 `PARADIGM_RECALL_OVERLAP_DAYS=30` 修复索引晚到、后补完整报告和短期车道失败。数据库为空、reset 或覆盖地图版本变化时，只把这些高信号车道扩到 `PARADIGM_BOOTSTRAP_LOOKBACK_DAYS=60`，不把宽领域关键词一起放大。重叠材料由证据指纹过滤，不会重复进入 LLM。报告前另有与技术 Rubric 分离的时效闸门，而且始终使用普通发现窗口：可核验的一手 `published_at` 在 `SOURCING_LOOKBACK_DAYS` 内才可称为新发布；高信号回补到 30/60 天不等于新鲜度也扩大到 30/60 天。老材料只有普通窗口内独立承接或指标量级变化才作为 update。首次入库、无日期页面、`dateModified` 和链接它的新仓库 `created_at` 都不能改变一手材料的发布时间语义；发布者自有仓库也不属于独立承接。手动审计已知漏项时可用 `PARADIGM_SEED_ARXIV_IDS` 精确回补，但 seed 只改变可发现性，不能提升 Rubric、发布者或编辑复核资格；arXiv 同时按 `lastUpdatedDate` 捕捉旧论文的新版本。跨代码提交恢复状态由数据库 schema 和覆盖地图版本共同决定，不再因 commit SHA 变化自动丢掉路线历史；云端状态按 `run_id` 保存不可变快照并恢复最近一份健康状态，仍可用 `reset_state` 主动清空。

研究数量不能由成本上限决定。发现层按日期窗口自适应翻页，所有发现材料先以 `last_analyzed_at=NULL` 写入可续跑 backlog；`PARADIGM_DISCOVERY_SAFETY_LIMIT` 可以让尚未执行的 arXiv 车道提前收尾，但不会对已经从各来源取得并合并的材料再次切片。外部可空标量在来源边界规范化，每条证据在 SQLite 事务开始前执行与恢复路径相同的 canonical round-trip；结构仍不合法的单条记录只隔离自身、按来源审计并计入 `research_incomplete`（兼容字段为 `run_incomplete`），健康同批记录继续提交。核心原点被拒绝时覆盖地图版本不得推进，避免以不完整检查点形成新的 bootstrap 基线。机制抽取、外部深挖和历史刷新再按可取消小批次执行。云端软时间预算只决定一次运行处理到哪里：执行队列在高信号材料与普通材料之间按 1:3 加权轮转，两类内部再交错本周新增和 FIFO backlog；显式补录、正式报告和官方/重点研究者仍获得更早注意力，但不能永久饿死普通论文。旧数据库中由宽查询或标题误标为 Technical Report、又没有当前可信分类来源的记录，会先按当前文档元数据与系统结构规则重新核验；降级只改变执行路径，不能改变 Rubric。只有已核验重点研究者，或 established 机构的正式系统报告/官方发布，才允许把 `observe` 候选送入一次有界复核，最终入选仍需通过 final Rubric、发布者与外部承接门槛。历史刷新按 `last_refresh_attempt_at` 从最久未尝试者轮转；成功但没有新承接也会清除旧故障标记，而超时/失败保留原快照并排到后续重试。研究阶段的 deadline 在发现完成后按真实剩余时间重新切分，慢冷启动不能提前把机制抽取份额吃成零。所有未完成项继续留在 backlog，不能冒充筛选失败。0 条交付且存在研究 backlog/执行故障时生成 `[阶段性研究]` 状态 memo 并披露已完成/计划量；研究已经闭合、只是可选信源或动态官方入口失败时生成 `[覆盖受限]` memo。只有研究与覆盖两条状态轴都闭合后才能得出“本期无新信号”。`*_SAFETY_LIMIT` 只有用户显式设置非零值时才作为额外运行熔断；最终研究去留仍只由版本化 Rubric 决定。

研究状态与交付状态遵循独立事务边界。发现到的原点先写入 backlog；覆盖地图版本则只有在逐领域核心 arXiv 车道与必需 OpenAlex 地景闭合后才推进，防止一次核心 API 故障把补扫缺口固化。OpenReview、Technical Report/重点研究者专项车道、官方网页或 Feed 的局部失败仍进入 `coverage_incomplete` 与邮件边界说明，但不会让仓库因一个长期失效的可选入口永久停在 60 天 bootstrap；这些入口继续依靠 30 天重叠窗口补抓。研究阶段完成后先保存证据、候选和人物结果，再把当期可报告候选与统计快照写入 `report_outbox`；之后才执行总编辑渲染、质量闸门和 SMTP。

outbox 使用 `pending_render → rendered → sending → delivered` 的活动状态链，并增加旁路状态 `quarantined`。渲染前先检查冻结候选是否仍满足当前人物与一手来源输入契约；确定性输入缺陷立即隔离。完整报告在模型内置修订后仍违反 URL、人物、势能或中文编辑契约时也立即隔离，不能把同一个确定性失败跨周重放。网络、超时和未分类运行异常按持久化 `render_attempt_count` 累计，默认 3 次后隔离。隔离与候选退回 `pending_deep` 在同一 SQLite 事务内完成，同时保留失败类型、时间和错误摘要供审计；活动队列只选择未隔离任务，因此一个坏快照不能永久形成队首阻塞。持久化报告在续投前仍要重新通过当前 URL 与编辑质量契约；规则升级后发现旧制品包含临时/缺失链接时，系统先把报告回退到待渲染，研究快照不回滚。

SMTP 失败与渲染隔离分账：前者保留已通过质量闸门的正文，且 `EMAIL_PUSH_REQUIRED=true` 时继续让任务失败；它不会因渲染次数耗尽被静默跳过。下一次进程先恢复最旧活动任务，不重新抓取或调用研究 Agent；成功交付后退出，并由云端在新状态 artifact 上传完成后用 `actions:write` dispatch 第二个 `reset_state=false` 的完整研究 run。若恢复任务被隔离，则同一进程直接继续新研究，因为旧快照已不再消耗长报告/邮件阶段；若本轮新生成的报告被隔离，数据库先无损保存研究状态，但当前运行仍以失败结束，避免把“未交付”误报为成功。只有 SMTP 确认返回（或明确关闭邮件、以本地文件为交付）后，才在一个数据库事务里同时更新 outbox 与路线的 `last_reported_signature`。邮件使用确定性 `Message-ID` 降低确认点崩溃导致的重复，但 SMTP 无法提供跨服务 exactly-once，系统承诺的是可审计的 at-least-once 重试。

每次完整运行同时生成结构化审计，记录信源返回量、arXiv/OpenAlex/OpenReview 查询与请求数、429/失败/熔断/未执行状态、漏斗、材料与路线的可见去留理由、模型阶段与 token 用量。所有并行发现源还有独立墙上时间上限：来源部分失败、全部失败、返回非列表契约或超时分别写成 `partial` / `query_failed` / `timed_out`，只降级对应来源并把整轮标为覆盖未闭合；不能把返回的空列表冒充成功零命中。多来源合并时，摘要长度与链接权威性分别比较：聚合页可以补正文和热度，但不能覆盖 arXiv、DOI、OpenReview 或官方发布页，也不能把 established 发布者、正式报告类型、重点作者命中和领域标签降级。没有可验证直接材料的 OpenAlex/Hugging Face 索引页不能通过报告原文闸门。每个模型阶段都校验输入与输出的身份集合/基数；漏回或混入当前批次以外对象时，只把对应输入保留为待重试。批次结构异常会递归二分到单条，健康同批对象仍能提交。机制抽取完成后先保存 `pending_deep` 候选，再标记原点已分析，保证异常最多造成重算而不会造成永久漏项；综合或最终 Rubric 未闭合也回到 `pending_deep`，并进入 `run_incomplete`，不能落入历史刷新或生成成功空报告。单个深挖或历史刷新批次出现未预期异常时保留原快照并继续处理同轮其他候选，执行失败与预算延期分账，不能写成技术淘汰。审计不保存 prompt、模型响应正文或模型私有推理；成功时随邮件发送，云端无论成功失败都尽量保存为 Actions artifact。Smoke test 与生产发现严格分离：单端点能力使用独立最小协议请求，多入口能力按配置顺序最多 failover 5 个入口，首个契约成功即停止；它只验证连接、鉴权和最小响应契约，并有逐项总时限，不导入生产召回器或复用领域车道、生产适配器、详情抓取、cursor/offset 分页器与 SQLite 持久化回环，也不能偏爱历史漏项中的公司或事件词。因此绿色 Smoke 是完整运行前置条件，不是生产路径验收。生产 arXiv 按“显式 seed → 正式报告 → 重点研究者 → 领域地图”使用请求预算，并使用较大传输页降低冷启动请求数；OpenReview 在确认持续 429 后打开共享熔断，剩余 venue/query 记为未执行而不是逐项重试。任何已经成功取得的高优先级材料都不会因后续车道失败而丢失。

## 7. 历史事故与通用回归契约

T‑Rex、Kimi‑K3 等历史漏项是阶段性的诊断输入，不是永久运行目标。一次事故修复完成后，样本中的标题、日期、arXiv ID 和整条特例链路必须从发布门退役；长期测试只保留它揭示出的通用契约，例如领域覆盖完整性、日期窗口与精确补录、重点研究者独立车道、无固定标题后缀的 Technical Report 识别、团队署名处理、正文回退、人物/实现/讨论分账及跨周路线对齐。日期窗口单测使用合成 Feed 和显式 UTC 参考时钟，避免 CI 日历漂移。某个真实漏项只有在复盘期间可以通过 `PARADIGM_SEED_ARXIV_IDS` 临时反查，不能进入每周 Workflow 的固定 seed 或成为未来发布阻断条件。
