| tokens | 901,180 | 1,140,437 | 无正式研究调用 |

“完成原点判断”包含资格预筛排除，不等于完成对应数量的全文研究。两轮正式运行都约 60 分钟；三次代码版本一致。9 月 11 日恢复的是 9 月 4 日状态，并非每周从空库开始。

已离线复现：固定日期测试过期；补齐机构信息触发假内容更新；旧快照覆盖新机制进度；pending_deep 不参与跨周相似匹配；导航栏的报告链接污染文档分类。当前没有生产状态数据库，不能把这些代码缺陷造成的实际重复量精确归因到全部积压。

本计划遵守以下边界：

- 保留机制 Rubric、发布者与独立承接核验、中文编辑、逐 URL 证据约束和关键人物要求。
- 调度优先级不是技术准入；延期、等待证据、执行失败和技术淘汰分别记账。
- 不固定交付篇数，不强行合并一份 Technical Report 内不同机制。
- 不清库，不删除历史交付，不把旧积压改个名称就宣布闭合。
- 不以扩容、增加定时频率或真实 API 调用作为默认实施动作；线上验收另需用户授权。
- 继续使用 Python、SQLite、GitHub Actions 与现有 outbox，不引入分布式任务平台。

## 2. 需要修正的核心抽象

### 2.1 四类状态不能混装

目前 TechnicalEvidence.raw 同时承担来源元数据、正文增强、机制执行进度和对某条路线的承接判断；ParadigmCandidate.status 又同时表达技术意见与执行状态。应逐步分离：

| 状态 | 回答的问题 | 更新规则 |
|---|---|---|
| 原始材料版本 | 原文是否发生实质变化？ | 只由来源事实更新，增强信息不得改变它 |
| 执行任务 | 某个阶段是否执行并提交成功？ | 按输入版本幂等、失败可重试、结果先于完成标记提交 |
| 技术判断 | 该机制成立到什么程度？ | 由 Rubric 和核验事实决定，不被超时覆盖 |
| 本期交付资格 | 本期为什么值得写、能否交付？ | 依赖窗口事件、人物与链接、编辑契约 |

同一技术可以“技术通过、本期无新事件”；同一任务可以“执行成功、技术观察”；这两种都不应重新做全部研究。

### 2.2 研究对象必须有稳定身份

- 材料身份：规范化的一手 ID/URL，并保留不同来源的别名与来源权威性。
- 机制身份：材料版本中的持久化 mechanism_id，名称只是可变标签。正式报告建立一次索引后，子任务直接引用其 ID。
- 路线身份：持久化 route_id；多个机制可沿共同 background 形成路线，同材料不意味着同路线。
- 承接判断：属于“证据 × 路线/机制”的关系，不是证据全局布尔属性。

不得仅用模型生成名称、机制数组下标或共享论文 URL 代替稳定身份。跨版本机制匹配不确定时保留关联候选，不自动吞并。

### 2.3 用本期事件驱动研究，而非每周重复处理全部档案

候选进入本期高投入研究应有可审计触发：窗口内的一手发布、原文实质修订、已核验的本期外部承接、必要的日期/身份补证，或明确的历史补课任务。

日期未知不等于过时，日期过时也不等于技术无价值：前者进入有界补证，后者保留观察并寻找本期更新。最终时效闸门继续保留；前置检查只是节约明显不必要的支出。

## 3. 目标模块与数据设计

不一次性拆掉现有大文件。先建立以下职责边界，再逐阶段替换调用点：

| 模块 | 主要责任 |
|---|---|
| runtime_clock.py（扩展） | 固定本轮 reference_time；可注入 UTC 业务时钟和 monotonic 耗时时钟 |
| paradigms/models.py（调整） | 兼容旧领域对象；新增显式版本、判断与资格结构，减少 raw 中的隐式协议 |
| database/paradigm_store.py（调整） | 原文/增强/执行写入边界、单事务阶段提交、旧格式兼容读取 |
| paradigms/work.py（拟新增） | ResearchTask、StageResult、阻塞原因及工作类别定义 |
| paradigms/scheduler.py（已实现时间轮转） | 三类任务公平调度与时间预留；成本上限、重试退避与背压仍待实现 |
| paradigms/eligibility.py（拟新增） | 批量预筛、日期补证、本期触发事件判定；不替代最终 Rubric |
| paradigms/evidence_validation.py（已实现基础核验） | 路线级独立性与实质讨论核验；完整持久化关系和独立复现核验仍待实现 |
| paradigms/analyzer.py（渐进调整） | 保留抽取/综合/人物能力，返回结构化阶段结果而非修改执行账本 |
| agents/paradigm_orchestrator.py（收缩） | 建立 RunContext、调度处理器、提交结果、组装报告候选 |
| main.py / run_audit.py / notifications / workflow | 产品结果状态、报告交付、审计与云端恢复 |

### 持久化的最小增量

复用现有 evidence_state、paradigms、paradigm_evidence、report_outbox；按实施批次增加必要字段/表，不预先堆叠全部 schema。

1. evidence_state 明确保存来源版本及 signature_version；派生资料写 evidence_enrichment，不接受旧候选把来源事实整块覆盖。
2. research_tasks 保存 entity_id、stage、input_revision/input_signature、policy_version、lane、status、attempt_count、next_attempt_at、run_id、执行占用标记与最后错误类型。
3. stage_results 保存与任务绑定的经过校验的结果、用量及结果版本。候选快照属于研究制品，不是修改来源事实的权限凭证。
4. paradigm_evidence 扩展为路线级证据关系，保存 relevance、independence、substantive、verification_basis、event_at、observed_at、核验版本与未闭合原因。
5. route_aliases 在稳定路线身份实施时新增；旧 key、既有交付记录均保留。

任务幂等键建议由 `(entity_id, stage, stage_input_signature, policy_version)` 构成。只有本期资格/交付等窗口相关阶段才加入 window_id；不能让每周窗口变化使原文抽取缓存整体失效。来源改变只失效依赖该改变的阶段，不触发全库无差别重跑。

任务状态最少区分 pending、running、succeeded、retry_wait、blocked；预算未分配仍是 pending 并记录原因。technical_verdict 和 delivery_eligibility 单独存，不复用这些状态。

### 阶段提交契约

单个 SQLite 事务内完成：验证当前任务版本 → 保存阶段结果/候选 → 建立下游任务 → 标记当前任务成功。父报告是否完成由其机制子任务派生，不接受旧 payload 覆盖累计进度。对旧实现继续保留“下游先落盘、上游后完成”的兼容路径。

网络调用不放在数据库事务里。进程崩溃或超时允许任务重执行；数据库副作用幂等。不承诺模型调用或 SMTP 的严格 exactly-once，尤其是调用已发生但确认尚未落库时。

## 4. 分八批实施；每批均有验收门

### 第 1 批：固定时钟、建立故障与回放基线

修改 runtime_clock.py、相关 source 构造参数、orchestrator、日期测试；新增 tests/replay/ 的离线时钟、假服务和临时状态工具。

- 修复 test_official_repository_uses_external_material_date_not_repo_date：明确 reference_time，不把日期简单改成“今天”。
- 将一次运行的报告窗口固定到启动时刻；跨午夜、补跑、恢复不能用不同 now 得出不同新鲜度。
- 为前述状态覆盖、假内容变更、pending 匹配、导航污染分别增加最小回归。
- 新增失败状态之外的断言：外部调用次数、任务身份守恒、阶段完成数、报告是否有可追溯路线。
- 先建立基线；尚未修复的缺陷放在独立诊断集，修复对应缺陷时转为必须通过的发布门，不永久跳过。

验收：在多个参考日期、时区、跨周/跨月情况下结果一致；正常离线回归不读取 .env、不接网络；生产版本故障有确定性复现，不只依赖一次日志。

### 第 2 批：修复增量状态与研究检查点

主要修改 database/paradigm_store.py、database/state_migration.py、paradigms/models.py、orchestrator 的提交点；新增任务/结果存储接口。

- 替换 _content_signature 的混合语义：来源机构信息与研究补充机构信息分开；补正文、人物、指标、分类器升级不得伪装为原文变更。
- 禁止 mark_evidence 在候选落库时无条件覆盖较新的来源/进度；拆为写来源观察、写增强、提交阶段结果的接口。
- 将 Technical Report 索引和子机制进度迁出 evidence.raw；进度单调性以“同一来源版本和同一算法版本”为边界，真实新版本允许新任务。
- 原点抽取、深挖子阶段按完成单位及时提交，不等整段 30–40 分钟工作全部结束才保存。
- 对 running 任务使用本轮 run_id 与尝试版本；重启时回收失去执行者的任务，迟到结果不得覆盖新版本。

验收：增强后重发现，原点模型调用为 0；旧快照不能把 2 个完成机制变回 1 个；任意提交边界注入崩溃后，既不漏候选，也不出现成功任务缺结果。并验证真内容变更仍能触发恰当重算。

迁移要求：先在副本上升级下一个 schema 版本；不得将 signature 算法变化批量记成原文变更。旧库无法分离的混合字段标 legacy_unverified，保留已完成结果；后续获得真实来源快照时建立新基线，不自动付费全库重审。旧执行记录只有可核对输入版本时才复用，否则保留为待核验历史结果。

### 第 3 批：修好来源事实、文档身份与日期

主要修改 sources/priority_research_source.py、sources/arxiv_document_source.py、sources/official_repository_release_source.py、paradigms/publication.py、paradigms/discovery.py。

- HTML 正文与链接都限制在可识别的文章区域；nav/footer/关联推荐中的 Technical Report 不能给当前文章授予报告身份。
- 报告分类保留“哪条材料证明该类型”的定位依据。当前文档引用另一报告，与当前文档就是该报告，必须区分。
- canonical_url 用于持久引用，fetch_url 用于下载。HF blob 页要解析实际文件入口；PDF 同时检查响应类型/文件特征，不能只看路径以 .pdf 结尾。
- 保留 published_at、modified_at、observed_at、date_basis；无日期只补证，禁止拿仓库创建时间代替外链论文日期。
- 页面正文、作者、文档链接必须绑定同一工作，不能把首次找到的任意引用文档当作本工作的全文。
- 对持续失败入口保留失败账本和可用替代车道；零解析与真正零发布分开。先修已知关键入口，不继续扩张信源数量。

验收：导航无关报告不会升级文章；HTML 假 PDF 不触发 PDF 解析；稳定 URL 不被签名跳转地址污染；来源合并不覆盖更权威的一手事实；日期未知不会自动进入“本期新发布”。

### 第 4 批：稳定机制/路线身份，补上承接核验

主要修改 paradigms/clustering.py、database/paradigm_store.py:attach_history、analyzer、enrichment、rubric、scoring、models，以及相关社区来源。

- pending_deep 参与身份对齐，但不参与“已完成路线”的资格推断；身份匹配和研究完成状态分开。
- 报告子机制使用持久化 ID，模型改名不产生新任务；同一报告的不同干预不得仅凭共同来源合并。
- 路线合并保留 alias、证据关系、历史交付和合并理由；模糊相似只给候选匹配，不强制合并。
- 增加候选级承接核验：读取允许访问的公开正文/实现信息，核对提出者与讨论者、当前机制关联、行动类型和事件时间。
- HN/X/GitHub/Tavily 返回的是发现线索或来源事实；验证器补齐关系结论，而不是在 source 中直接给所有第三方打 independent 标签。
- Tavily 线索只有在独立获取并核验原始页面后才能产生新的已验证证据对象；不直接修改索引命中的标签来“升级证据”。
- rubric、scoring、freshness、报告势能段共用同一核验结果，消除前面算承接、后面又不承认的口径分裂。
- 指标增量绑定前后两次观测和时间区间；历史 metric_delta 不能永久激活后续每一期报告。
- 社区正文只在当轮处理，持久化核验理由、URL、时间与必要结构化事实；不得因新增缓存违反现有正文清理约束。

验收：同名异机制不误合并、同机制改名不重复排队；同一讨论对路线 A 有效，不自动对路线 B 有效；自发帖/聚合页/泛讨论不能通过；已核验的本期独立承接可使旧路线成为 update。

### 第 5 批：把大阶段串行流程改为可续跑任务调度

主要修改 agents/paradigm_orchestrator.py；新增 scheduler/work/eligibility；拆开 EvidenceEnricher 的文档、外部证据、人物步骤。

三类调度车道：

- current：本期原点和日期/身份补证，尽早完整走到交付资格。
- updates：历史路线的新证据检索、核验及必要增量研究，有独立预算。
- backfill：历史未完成工作、报告未完机制与非紧急重试，保留最低服务份额。

资格预筛是独立可持久化任务，可持续消费普通材料，不再等待当前小批次完整 Rubric 结束。批大小按上下文预算与响应可靠性控制；遗漏、外来 ID、重复 ID只影响对应对象，不丢健康结果。

每条路线按需执行：来源/日期核验 → 资格与机制种子 → 外部承接核验 → 技术综合 → 人物补全 → 最终 Rubric/本期资格 → 报告。旧路线若没有新事件，先做低成本更新检查，不再次完整写机制档案。

技术初判先于完整人物履历，但不得因人物题暂未完成就把临界候选提前技术淘汰；满足技术必要条件的候选继续人物核验，最终分数仍由完整契约计算。

调度采用成本感知的加权轮转与等待时间补偿；优先级只影响出队。保存阶段输入签名、完成结果和重试原因；模型输出结构错误、网络失败、预算延期分开退避。单条路线、单份报告不能连续占满整类预算。

在不增加现有研究时长的前提下，可先回放以下 60 分钟分配：来源/元数据 5 分钟、批量预筛 8 分钟、本期研究 30 分钟、历史更新 10 分钟、补课 4 分钟、检查点与收尾 3 分钟。它只是实验起点，不是已验证配置；空闲份额可借用，有任务的更新/收尾预留不可被提前耗尽。

报告沿用独立有界预算，并以 Actions 的整个 job 截止时间作最后上限；设置总预算与在途调用预留，不能让并发调用各自都花完“剩余预算”。

验收：上万条旧任务存在时，确定的本期候选仍能走到终点，历史刷新非零；已完成技术综合后人物接口失败，下次只补人物；任务中断不会回到整条 deep pipeline 起点；慢任务不能饿死其他车道。

### 第 6 批：减少模型重复劳动，统一请求契约

主要修改 agents/llm_utils.py、paradigms/analyzer.py、Rubric 输入输出、skills 下对应研究提示词。

- 第一次抽取只产出后续判断需要的机制种子和必要 Rubric 依据；完整 background、心智模型与写作叙事只在深挖生成，避免前后反复写同一套长字段。
- 不删掉未知、反事实、训练/推理区别与关键接口；压缩重复而非削弱技术研究。
- 普通资格预筛、机制分析、承接核验、人物、编辑有独立 ModelProfile 接口；初期可映射现有模型，不强制更换供应商或新增密钥。
- 为批量输入/输出定义确定性 schema、身份核对与局部修复；记录 finish_reason、输入/输出/reasoning tokens、延迟和失败分类。不能把全部 JSON 失败都当成需要重跑完整长回答。
- 缓存按阶段输入、Skill/Rubric 版本和模型配置版本命中；不能跨不同材料版本复用旧结论，也不让无关提示词变化清空全部缓存。
- 不通过强制非思考、提高 max_tokens 或切换模型赌效果；真实供应商参数与小样本效果需在实施/授权验收时核验。

验收：相同输入重放不增加研究调用；长报告续跑不重复建立索引；坏 JSON 仅修复失败单位；用固定材料比较改前/改后用量与技术判断一致性。离线模拟不能证明真实模型质量或吞吐，必须明确其边界。

### 第 7 批：对齐报告、审计与 Workflow 的产品结果

主要修改 main.py、run_audit.py、reports/paradigm_generator.py、notifications/email_notifier.py、.github/workflows/weekly-radar.yml。

- 保留 outbox、路线草稿缓存、隔离恢复、逐 URL 校验和邮件确认后更新签名的既有保护。
- 新增统一 Outcome：技术判断、时效资格、人物/链接、编辑、实际交付分别记账；record_candidate 不再提前把技术通过写成“进入报告”。
- 修正 pipeline_result 中 `fresh_research_completed = not recovered_only` 的语义：开始过新研究不等于完成新研究，改为明确的 executed/completed 与各未闭合轴。
- 同时报 current_window_pending、historical_backfill_pending、retry_pending、blocked_pending、oldest_pending_age、freshness_rejection_after_deep、重复计算调用数和队列净变化。
- 全局未完成与本期未完成同时披露；不能通过移出 active 队列、改统计分母或更名观察池制造“完成”。历史积压只允许作为内部续跑进度，未闭合时不得交付阶段性内容；研究与已配置覆盖均闭合才发送正式报告，空结论仍不能外推为整个 AI 领域没有进展。
- 产品失败告警与进程失败分开：预算耗尽且没有可交付结果、关键工作超过服务目标时给出可行动告警。SMTP 成功不代表研究成功；质量契约失败仍禁止正式交付。
- V0 首版维持原定时频率。增加纯本地/手动的 resume-research 工作模式时，要跳过重复发现并固定原窗口；将来若需要自动续跑，必须有跨 run 的预算、最大次数、链 ID、状态先上传和去重，另行授权开启。

验收：技术通过但时效失败不会显示已报告；预算未完成不会输出 complete_no_signal；旧交付恢复仍先保存状态再独立排队新研究，不与新任务叠加在同一 90 分钟进程；发送失败不写成已投递。

### 第 8 批：多周回放、状态迁移演练与线上验收

新增 scripts/replay_research.py、tests/test_research_replay.py 及脱敏固定 fixtures；使用真实编排器/数据库/报告契约，仅替换网络、模型、邮件和时钟。

至少覆盖以下场景：

1. 上万历史任务 + 每周数千发现记录：重复记录不重复分析，本期候选与历史更新各有进展。
2. 连续三周无一手新路线，但第二周有真实独立承接：只第二周产生相应 update。
3. 完整执行但无合格信号：得到真实、范围明确的空结论；未执行则不能得到同一种结果。
4. 一份报告含多个独立机制；中途崩溃、旧快照回写、原文新版本出现：无永久漏项，无跨版本伪复用。
5. 403/429、HTML 伪 PDF、模型漏回/截断、人物同名、邮件失败、artifact 失败分别注入。
6. 同一周再次运行：研究缓存与交付去重均生效；不能由报告措辞变化触发同一事件再次投递。
7. 使用旧 schema 真实状态副本迁移：保留路线、证据关联和已交付历史，对疑似重复只生成可审计映射。

模拟服务必须包含延迟、返回大小、故障分布与取消行为，并使用固定随机种子或确定性故障序列；不能让所有 mock 立即返回后宣称一万条生产工作可在一分钟完成。合成吞吐实验与人工标注的研究质量样例分开，样例日期均注入时钟，历史发布名称不得成为每周固定 seed 或发布门 canary。

## 5. 稳态与 V0 验收标准

不要用“268 项变成 400 项”或“每周交付至少 N 条”作为 V0 标准。

硬性正确性：

- 所有入选路线通过中文、机制、人物、独立承接边界和逐 URL 契约；执行异常不能变技术否定。
- 任意研究提交边界恢复后，已完成结果可用；无任务成功而下游对象缺失。
- 相同来源版本重放，不重复调用已完成的机制研究；仅未确认提交的失败尝试允许重算。
- 当前窗口、历史任务、预算延期、等待证据和外部覆盖缺口均可区分。

候选服务目标（先由回放校准，再确定生产阈值）：

- 合格本期样例在一个完整运行预算内走到交付资格，不能被历史队列饿死。
- 有待刷新路线且外部服务可用时，每轮都有更新检查；等待年龄不持续失控。
- 在声明的负载与预算内，连续多窗口活跃研究队列净流入不持续大于净完成量；历史补课另报进度。
- 记录来源召回率/人工样例命中率，防止靠大量误筛制造吞吐改善。

稳态约束：有效任务到达率必须低于可持续处理率，并留重试余量。若修复与成本压缩后仍不成立，应明确给用户选择：缩小经过声明的研究范围、增加预算、或增加运行频率。不能承诺在固定预算下无限处理所有来源，也不能私自牺牲质量门槛。

线上分级验证必须在用户授权后进行：先指定小样本、无邮件、明确调用/时间预算；再一次保留历史状态的完整研究；验证同窗重跑/续跑不重复研究或投递；最后观察连续计划窗口。三周业务场景首先在本地加速回放，不再等待三个真实周来发现确定性错误。真实模型输出、第三方可用性和定时生产稳定性不能只靠离线结果证明。

## 7. 提交顺序与文档联动

建议每批形成独立、可评审的小提交组，顺序为：时钟/基线 → 状态与检查点 → 来源事实 → 身份与承接 → 调度 → 模型效率 → 结果语义 → 回放/上线。测试从第一批开始伴随修改，不留到最后；最终第八批验证跨批行为。

每批最低检查：相关单测、迁移回环（涉及状态时）、离线全套、compileall、git diff --check；全部禁止真实网络与真实邮件。针对现在的日历错误，先修复再恢复全套发布门，不以删除测试通过验收。

研究逻辑变化需同步检查：skills/paradigm_extraction/SKILL.md、skills/paradigm_synthesis/SKILL.md、skills/researcher_trajectory/SKILL.md、skills/weekly_research_memo/SKILL.md；同时更新 origin_eligibility、technical_report_index/mechanism、weekly_route_draft 等实际调用提示词。模型输出字段必须同步解析器、领域对象、报告器和测试。

配置变化同步 config.py、.env.example、docs/CONFIGURATION_CHECKLIST.md、workflow env、healthcheck.py 和 offline_checks.py 的安全默认值。信源变化同步信源说明.md；云端/邮件语义同步 docs/CLOUD_AUTOMATION.md；最终同步 README、设计说明和体检结论，禁止继续把“离线通过”写成“生产 V0”。

明确不在本轮范围：替换整个研究方法、引入 Redis/Celery/向量库、扩张更多信源、自动猜测人物联系方式、降低中文/URL 质量门、强制每期非空、清库、未经授权增加 API 消耗或发送邮件。
