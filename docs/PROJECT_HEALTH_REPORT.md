## 1. 本轮交付的工程能力

- schema v8 固定研究批次，冻结窗口、seed、发现快照与覆盖账本；一个未完成批次跨进程恢复，不每次重扫并加入新一周材料。
- 原点、深挖、历史刷新有任务清单与版本回执；清单只增不减，刷新一次成功或无变化后不重复入队，运行中断另记尝试而非技术淘汰。
- 普通资格预筛默认 24 条，逐原点缓存健康结果；混合队列采用有界前瞻预填缓存，与小批完整抽取解耦，保持原执行顺序。遗漏、重复或外来 ID 不牵连健康同伴，同次访问不重复付费修补失败预填。完整抽取仍是机制 Rubric，不以吞吐降低门槛。
- Technical Report 索引持久化，每个成功机制立即保存下游候选与父进度；慢同伴/取消不会吞掉结果，健康分片在同轮有预算时继续。解释改名不改变已索引机制身份，不强并同报告不同机制。
- 独立路线深挖默认并发 2；综合/人物检查点可在同一固定批次跨周复用，相关输入、策略或模型配置变化使其失效并重建可执行队列。
- 人物轨迹逐身份保存成功结果；错误 JSON、缺字段和非中文解释不能缓存完成。并行阶段失败会取消并等待在途同伴，不放任后台请求继续消耗。
- 研究窗口与真实指标观测时钟分开；续跑的新发布/增长不倒填原周。社区临时正文不写入发现、候选或任务恢复快照。
- 只在任务与详细覆盖全部闭合后入 outbox；父状态、真实 SQLite 队列与统计相互核对。报告/SMTP 独立恢复，确认后才登记交付。
- 有界自动预算续跑已实现但默认关闭：同批次、状态先上传、纯预算延期、次数/研究时间/已确认 tokens 上限；源故障、执行错误或未知中断用量需修复后人工继续。未设置远程变量、未触发 Actions。
- arXiv 含重试共享三秒请求间隔，尊重长 Retry-After；HTTP 200 错误 Atom、非 Atom 和重复分页拒绝记为成功空结果。
- OpenReview 只扫描 forum 投稿，共享请求间隔/Retry-After，按可核验 count 分页；每页证据及 offset 先提交，429/取消不丢健康页，固定窗口续跑不从 offset 0 重扫；错误 count/重复页/提前空尾页不记完成。
- 新增逐入口验收 CLI 与 `source_check_only` 工作流：真实生产解析、临时 SQLite 回环、完整清单分母、有界请求/响应、去敏账本；完全绕开生产研究、状态与全部邮件路径。
- RSS/Atom 结构、alternate 链接、作者/日期契约统一；Follow Builders/HF 错误 JSON 不再成为成功零结果。官方仅年份日期保持未知，详情/PDF 解析错误计入缺口。
- NVIDIA 公开同源 publications 脚本限定适配、Sakana/CMU 根路径与 LILA 单页正文适配。人物连续性只接受有限数值或无损数字字符串，异常至多做一次保留事实的格式修复，仍不合规保持 pending。
- 历史刷新在社区/模型请求前核对原点版本；过期对象先保存可执行深挖快照，再转交依赖，刷新父任务仍在分母，只有当前版本深挖闭合后才能关闭。
- 模型请求统一记录耗时；取消传播且记为用量未知，不把预算取消漏出账本。验证器仍只记录一次成功/失败响应，模型参数与思考模式未改变。

具体接口异常：OpenReview 使用 source=all 翻到 offset 1000 后 429；人物 Baofeng Zhao 的连续性字段无效，单候选已隔离 pending。官方/KOL 403/429/404 仍进入覆盖缺口。补充 audit 确认官方仓库的实际一手外链失败是 facebookresearch/E2E-SWE 与 OpenBMB/Trident，不应把三个无 README 的噪声仓库一概当作覆盖阻断。源码中的具体入口故障仍待 Runner 验收，不删除。旧 audit 没有逐请求耗时，且预算取消请求可能漏记，所以 86 次已记录调用/114.5 万 tokens 不是完整费用证明；新审计补齐耗时与未知用量。误筛率与真实质量仍需另行授权的小样本验证。

日志中的“覆盖率 85%，低于 85%”是百分比取整造成的诊断歧义，不据此降低结构门槛；本轮改为两位小数，并用 11/13=84.62% 与 85.00% 的固定回归样例验证。

日志中的失败入口包括 OpenAI research index、Physical Intelligence research、TRI publications、xAI news 的 403/429，Z.ai blog 的 404，以及 Gary Marcus/Zvi Feed 的 403。本轮公开只读检查确认 Z.ai 博客根路径仍 404，sitemap 仅产品/账号页，不是等价研究索引；不能替换后假称研究覆盖恢复。其他公开端点检查亦未取得可交付的完整覆盖证据。未删除这些配置，少数失败仍阻断闭合。

OpenReview 已改成 query/page 独立持久化，其他来源部分失败仍可能重试整个适配器。如果真实生产某个来源永远无法在 600 秒内完成，需要据详细 audit 拆开其能力回执，而不能提高所有源超时赌成功。外部增强未进入综合检查点仍须重取临时正文，保留隐私边界；逐人物 API 内部及独立承接关系表、跨来源版本路线 alias 并非全部自动化能力。它们是否造成真实容量/质量阻断，需要副本回放测量，不宣称所有长期设计项已完成。

自动链默认关闭，所以大于一次预算的真实负载不会自行一天完成；开启额外 run 是成本选择，不能由代码重构擅自启用。默认四轮/四小时额度也不是对任意 workload 的完成保证。没有真实到达率、模型延迟/用量与误筛样本，不能给可信的 V0 日期或费用预测。

## 4. 进入生产 V0 的验收顺序

1. 已取得 run 37899070924 的 audit 与健康 state，在临时副本验证迁移和数量守恒；后续运行继续使用同 run 成对制品核对，不能混用不同时期日志/状态。只读诊断可用 `scripts/inspect_capacity.py`，不恢复生产库、不联网。
2. 先在 Runner 执行 `source_check_only=true`、`reset_state=false`，逐个失败来源验证等价官方公开入口/协议。本地公开样本不能替代云端 IP/CDN 与真实配置验收；不删团队、Feed、待办或缩分母“修好”。确需缩研究范围时由用户明确决定，并建立新的声明范围。
3. 经用户授权后进行有界小样本真实 API 验收，先关闭邮件，记录延迟、用量和人工研究质量；再做保留旧状态的完整闭合、同窗恢复与去重验收。SMTP 发信需单独明确授权。
4. 校准单窗口真实工作量与可持续处理率，确定是否开启预算续跑及可接受额度。完整报告/空结论必须可解释，不靠每期强行非空。
5. 验收实际云端代码指纹、详细覆盖闭合、状态上传、报告质量、交付确认及后续计划窗口。当前没有执行这些真实流程。
