## 根因与对应修复

1. **渠道策略冲突，影响 55 候选。** 线上仍设置 Tavily 请求上限 12。账本相较上轮新增 12 个已确认 basic credits，达到本地上限后不再调用。GitHub/HN 已完成，调度层 blocking_searches(allow_partial=True) 放行，综合器却调用旧 incomplete_searches 并抛错，MAIN 请求未发生。现按批次传播同一策略，综合、刷新与最终交付使用同一判定；失败回执/盲区保留，全渠道失败仍待办。到限容量提醒不是候选数量门。
2. **机制类型没有真正的结构契约。** 旧 Model Card 种子含 `[["architecture"]]` 与未知 `training_methodology`；新缓存报告又返回 type/detail 对象数组。旧 normalizer 把它们变成 other，下发题目错误，回答改变类型后又按另一类型验收，重试必然漏题。现新索引逐项严格验枚举/身份、不丢坏兄弟；机制评估给出全部可选类型的实际问题。旧种子原样保留保证 key/ID 稳定，已知包装只在请求视图无损读取，未知分类在已有机制请求中重判，不额外重跑索引。
3. **成功缓存弱校验。** 原只要求几个字符串便复用已完成机制。现复核类型、Rubric 版本、全题/选项与决策；旧坏结果可由有效修复替代，健康判断仍优先于陈旧写入。普通原点漏 rubric_answers 的重试带入上轮对象及实际题目；两次仍失败则保持待办，不由程序补 unknown 或否定。
4. **账户页误作原点。** htn demo README 中获取 API Key 的链接被选为外部一手材料，200 登录 HTML 被拼入摘要。现 URL 与最终重定向的账户/登录/政策/挑战判定共用，旧 URL 也不能进入报告；无合格外链时只有通过现有原生机制资格的 README 才可作 original_implementation。旧误抽候选仍接受完整复核，不靠删任务造闭合。
